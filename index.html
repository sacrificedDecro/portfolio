What I've built

Dead rails - drag, weight & throw
A multiplayer drag-and-throw system for physics objects tagged as draggables. The server checks the object, distance, ownership, and anchored state before assigning network ownership and applying AlignPosition and AlignOrientation. Object weight changes responsiveness and throw speed, which is capped by configuration, while running footsteps fade in and out through server-controlled state.
Gist
Simple combat system
A server-authoritative melee system with M1/M2 combos, sprint bonuses, blocking, back attacks, knockback, blood, and randomized impact sounds. The server applies cooldowns, checks the player state, creates short-lived hitboxes, and applies damage from server-side contacts. Training dummies are included for testing attack and block interactions.
Gist
R6 & R15 ragdoll system
A ragdoll system for R6 and R15 characters that replaces enabled Motor6D joints with BallSocketConstraints and handles AnimationConstraints. The server controls the ragdoll state and physics ownership, limits rapid toggle requests, and keeps death ragdolls permanent while manual ragdolls can be released. The client adds a ContextActionService toggle and moves the camera to the head while ragdolled.
Gist View on Roblox
Inventory slot UI & custom interact prompt
A server-validated inventory and interaction system with three configurable slots, tagged world items, custom Highlight prompts, equip and drop tools, and server-confirmed feedback sounds. Items are checked for ownership, distance, free slots, and valid master definitions before pickup; inventory data is claimed and periodically renewed through a DataStore session lock. The client UI supports slot activation and keyboard shortcuts, while footsteps are timed from the R6 walk animation.
Gist
Tink — game framework
A strict-typed Knit-style framework for Roblox services and controllers, built around Spark modules rather than the archived Knit codebase. It provides remote signals, remote properties, unreliable signals, per-player rate limiting, module discovery, and staged startup with per-service failure isolation and timeouts. The framework uses the evaera Promise library for asynchronous lifecycle hooks.

How I work

Pay per task by default. Each commission is broken into clear deliverables, and you pay for each one as it's delivered. If you'd rather use a simple 50/50 split, with half upfront and half on delivery, that works too. No revenue share and no "pay when the game ships." Gift cards and crypto aren't accepted; ask if you have something else in mind.

Ownership

As soon as a task is paid for, that code is yours. You can modify it, ship it anywhere, and I don't keep a copy.

Refunds

You can stop at any time. With per-task work, you only pay for what has been delivered. With 50/50, the upfront half is refundable until I start.

Availability

I'm available daily from 18:00 to 1:00 (UTC+3). I reply within hours on Discord and more slowly by email.
